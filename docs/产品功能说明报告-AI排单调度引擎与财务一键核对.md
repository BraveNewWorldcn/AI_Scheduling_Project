# AI排单调度引擎 + 财务一键核对 —— 产品功能说明报告

> 适用范围：项目交接文档 / 面试案例素材（非程序员用AI独立开发系统）
> 撰写日期：2026-06-09

---

## 一、一句话定位

**为消防设备供应链场景定制的AI自动化工具，以飞书为快速验证平台（公司主数据在OA），解决订单高峰期人工排单和财务核算的瓶颈——把日常1-2小时的人工排单压缩到10分钟（3分钟导数据 + 30秒排单 + 剩余时间人工审核确认），财务核算从2小时压到5分钟。**

---

## 二、解决了什么痛点（Before / After）

| 维度 | Before（无工具时） | After（有工具后） | 量化变化 |
|------|-------------------|------------------|---------|

| **库存缺货分析** | 人工逐SKU对照库存表，遇到新产品或BOM变更要来回问人 | 自动匹配SKU标准表，缺货SKU自动标注缺口数量+预计到货日期 | 错误率从人工约5%漏检→系统0漏检 |
| **财务核算（核心痛点）** | 跨3张表手工匹配计费规则，包干/单采分类靠人工判断，一个合同可能重复算3次才确认 | 一键同步→自动匹配Spec_ID→自动分类核算→汇总回写，阈值可调 | 核算耗时从**2小时→5分钟**，**压缩96%**；人工核对金额锁定防重复计算 |
| **客户查单** | 客户在群里@商务"我的订单什么时候发货"，商务切到OA/飞书手动查→截图回复，平均5-10分钟/次 | 客户在群内@机器人→输入项目名或合同号→自动返回交付状态卡片，3秒响应 | 响应耗时从5-10分钟→3秒，**压缩99%**；商务不再被打断 |
| **日报推送** | 每天下班前手动汇总排单/缺货/发货数据，整理成文字发群，约20-30分钟 | 系统自动读日报表→AI生成摘要→三线推送（采购卡/计划卡/老板卡），全自动 | 耗时从20-30分钟→0，**省掉每天近半小时的重复劳动** |
| **信息一致性** | OA是主系统，飞书是自建的辅助验证平台。OA和飞书之间的数据依赖人工同步，容易出现版本不一致 | OA导出数据→飞书导入，通过合同编号+Upsert机制保证飞书侧不重复不丢失；同步时保护人工字段不被覆盖 | 飞书侧数据始终保持与最新导入一致，消除了自建平台的数据漂移问题 |

## 三、核心功能模块

### 模块1：AI排单调度引擎（核心）

**做什么**：从OA导出销售订单Excel → 导入飞书 → 自动读取订单明细、SKU标准、库存快照，计算每个订单的缺货情况和建议发货日期，按产能限制自动排列生产计划，将结果写回飞书多维表格供人工审核确认。

**怎么做的——关键决策**：

1. **为什么在飞书上自建系统，而不是直接在OA上开发？**
   - 公司主数据跑在OA上，但OA改一个字段、加一个流程需要走IT排期，响应周期长（数天到数周）
   - 飞书多维表格可以随时加字段、改结构，非技术人员几分钟就能完成，适合快速验证和迭代
   - 飞书提供标准REST API（分页读取、批量写入、Upsert），足够支撑日常10单/高峰30+单的规模
   - 定位是OA的**补充验证系统**——OA是唯一数据源，飞书是快速分析和自动化执行层，数据从OA导出Excel再导入飞书

2. **为什么用并查集产能调度而不是简单排序？**（详见第四节技术架构）

3. **库存可用量计算公式**：
   ```
   库存可用量 = 当前库存数量 - 已确认订单SKU需求 - 已预留数量
   ```
   已发货订单不再占用库存。人工已确认的订单参与锁单库存占用，AI重新排单时不会覆盖人工决策。

4. **人工确认保护机制**：
   - AI只写入`待确认`状态。`已确认`和`已发货`由人工在飞书中维护，系统绝不覆盖
   - 已确认订单的库存占用会被保留，后续排单自动扣减

5. **工作日自动顺延**：所有建议发货日期自动跳过周六周日

6. **新增订单保护**：本次加载到的全新订单（之前缓存中不存在的），即使飞书API回填有延迟，也不会被漏排

**完整操作流程**：从OA导出数据（人工操作，不在系统内）→ Excel导入飞书（约3分钟）→ 触发排单（约30秒，含读表+库存匹配+缺货ETA+产能调度+写回）→ 人工审核确认结果并通知相关人员（剩余时间）。总计约10分钟，相比原来1-2小时大幅压缩。系统真正解决的瓶颈是30秒的排单计算——人工做这件事需要逐个订单查库存、算日期、排产能，30+单时极易出错。

### 模块2：财务一键核对

**做什么**：将销售订单数据同步到财务对账表，自动匹配计费规则，按包干/单采分类逐合同核算，计算AI项目金额并回写。

**怎么做的——关键决策**：

1. **同步和核算分离**：
   - 同步（`/finance/sync`）只管把销售订单数据搬到对账表，匹配Spec_ID，不计算价格
   - 核算（`/finance/calculate`）只做纯内存计算+批量回写，不重新读销售订单
   - 好处：数据源（销售订单）和核算结果（对账表）解耦，核算出错不会污染数据源

2. **Spec_ID三层匹配策略**（`_match_spec_id`）：
   - 第一层：**精确匹配**——产品名称 == 产品名称 AND 规格 == 规格型号
   - 第二层：**别名匹配**——同规格下，产品名称包含别名 OR 别名包含产品名称（双向包含）
   - 第三层：**关键词匹配**（仅AC-RB800规格）——产品名称含"主键盘"→SPEC-RB800-KZP，含"电话"→SPEC-RB800-PHONE等6组规则
   - **为什么选关键词而不是调LLM？** 详见第四节技术架构

3. **包干项目完整性自动检查**：
   - 检测包干合同是否缺少"消防远程控制服务费"和"消防远程控制包干费"两行，缺少则自动补行
   - 检测主键盘合计数量 > 阈值（默认3），超出部分自动新增"消防远程控制设备费"行
   - **为什么需要这个？** 实际业务中，销售下单时经常漏填这两行服务费，导致财务核算时少算费用。自动补行确保不遗漏收入

4. **人工核对金额锁定机制**：
   - 只要总表"人工核对金额"字段非空且非零，该合同**完全锁定**：同步不修改，核算不重算，回写不覆盖
   - 这是财务数据的"安全气囊"——人工确认过的数字不能被AI覆盖

5. **三种计费模式**：

   | 场景 | 条件 | 是否计入包干 | 单采数量 | 单采价格 | 小计 |
   |------|------|------------|---------|---------|------|
   | 单采设备 | 计费方式=单采 ∧ 包干阈值=0 | 否 | 合同数量 | 计费规则单价 | 合同数量×单价 |
   | 包干阈值内 | 计费方式≠单采 ∧ 合同数量≤包干阈值 | 是 | 0 | 0 | 0 |
   | 包干超阈值 | 计费方式≠单采 ∧ 合同数量>包干阈值 | 是 | 合同数量−阈值 | 计费规则单价 | (合同数量−阈值)×单价 |

6. **同步时的字段保护**：同步对账总表时，6个字段从销售订单同步（合同编号、下单日期、客户名称、项目名称、商务、代理商），但5个字段**绝不覆盖**（项目类型、备注、AI项目金额、人工核对金额、AI费用检查）。同步明细表时，4个核算结果字段（是否计入包干、包干合同单采数量、单采价格、小计）同样保留不覆盖。

7. **计费规则表只读保护**：代码中明确标注"产品计费规则主表禁止AI改写，仅人工维护"，没有任何路径会写入计费规则表。

8. **审计回溯脚本**（`audit_rules.py`）：6项独立检查（数据完整性、设备费规则、电话规则、关键词匹配、计费覆盖、汇总统计），可随时独立运行，不依赖核算流程。

**量化结果**：单次核算约30秒（读4张表 + 完整性检查 + 逐合同计算 + 批量回写），处理流程约1500行明细数据，最多3次飞书API批量写回调用。

### 模块3：客户订单查询机器人（对外）

**做什么**：飞书群里的外部客户@机器人，输入项目名称或合同编号，自动返回该订单的交付状态卡片。

**怎么做的——关键决策**：

1. **双App WebSocket长连接架构**：
   - 两个独立的飞书应用通过 `lark-cli` 的 WebSocket 长连接接收消息
   - 不需要公网URL（传统Webhook机器人必须暴露公网回调地址）
   - 两个App端口独立（各端口9000），互不影响

2. **四层查询漏斗**：

   ```
   第一层：身份提取 → 通过飞书通讯录API获取客户公司名
   第二层：模糊匹配 → difflib.SequenceMatcher + 关键词评分，在公司订单子集中搜索
   第三层：消歧卡片 → 匹配到多条时，弹出编号选择卡片让用户确认
   第四层：精准交付 → 返回包含交付状态的飞书互动卡片
   ```

3. **为什么用difflib而不是调LLM？**（详见第四节技术架构）

4. **信息隔离设计**：
   - 客户看到的信息：订单编号、项目名称、**非技术性的交付状态描述**（如"已排期，预计X月X日发出"）、物流信息
   - 客户**看不到**：内部成本、采购价、供应商信息、库存细节、产能数据
   - 所有回复卡片用面向客户的语言重写，不含任何内部术语

5. **智能关键词提取**：自动去除"帮我查一下""那个""请问"等口语噪音词，保留项目/设备/交付相关实词；支持复合词拆分（在"项目/设备/系统/工程/园区"边界处断开）

6. **去重保护**：维护最近5000条已处理事件ID的集合，防止重复消息

**量化结果**：从用户发消息到收到卡片，全链路约3-5秒（身份提取1秒 + 数据加载2秒 + 匹配+卡片生成1秒）。

### 模块4：内部供应链AI助手（对内）

**做什么**：飞书群里内部员工@机器人，输入自然语言指令（如"日报""库存""延迟""合同编号"），自动返回对应的供应链管理卡片。

**怎么做的——关键决策**：

1. **基于Webhook的回复模式**（而非WebSocket长连接）：
   - 内部机器人和外部客户机器人使用了不同架构
   - 内部机器人通过飞书事件Webhook接收消息，通过飞书消息API回复
   - 支持加密事件解密（AES-256-CBC）

2. **自然语言关键词匹配引擎**：按优先级从高到低匹配意图：

   | 用户输入包含 | 触发功能 | 返回内容 |
   |-------------|---------|---------|
   | 日报/今日/报告 | 读取今日排单日报 | 订单总数、新增、紧急、发货、延迟统计卡片 |
   | 库存/缺货/物料 | 读取库存快照 | 缺货SKU明细、短缺数量、最紧缺物料 |
   | 待确认/排单进度 | 读取排单状态 | 待人工确认订单列表、排单完成率 |
   | 延迟/延期 | 读取交付状态 | 预计延迟订单+延迟原因 |
   | 合同编号 | 精准查询 | 该合同的完整交付链路信息 |
   | 飞书文档链接 | AI文档扫描 | DeepSeek对文档内容进行摘要+关键数据提取 |

3. **飞书文档AI扫描**：自动识别消息中的飞书文档链接，调API读取文档内容，送DeepSeek做摘要，结果以卡片形式返回——不需要人工复制粘贴到AI对话框。

4. **今日数据校验锁**（详见第四节技术架构）

5. **防呆设计**：
   - 闲聊/问候自动识别，返回功能引导卡片（告诉用户能做什么）
   - 无法识别的输入给出明确的帮助提示，不瞎猜

**量化结果**：日均处理20-30次内部查询，每次1-3秒响应。飞书文档扫描约5-8秒（含AI处理时间）。

### 模块5：三线日报推送

**做什么**：每天早上自动运行，读取最新排单日报数据，通过DeepSeek生成运营日报摘要，以三种不同视角的卡片分别推送给采购、计划、老板三条线。

**怎么做的——关键决策**：

1. **三线差异化推送（不是一份日报Copy三份）**：
   - **采购线（红/橙卡）**：聚焦缺货SKU、紧缺物料、需紧急采购的品类——采购只看自己需要下单的东西
   - **计划线（蓝卡）**：聚焦排单完成率、产能利用率、待确认订单——计划员看全局调度状态
   - **老板线（变色卡）**：红=有严重延迟/缺货，黄=有预警，绿=一切正常——老板一眼判断要不要介入
   - 三条线通过三个独立的飞书Webhook URL发送，每家机器人身份独立

2. **DeepSeek AI加工**：原始数据是数字，AI将其转换为自然语言摘要——"今日共排单48份，其中3份因XX物料缺货预计延迟至6月12日，整体交付健康率92%"

3. **日报+飞书文档+任务联动**：
   - 日报内容同时创建为飞书文档（存档可回溯）
   - 异常事项（如延期订单）自动创建飞书任务分配给对应责任人
   - 一天跑完7步：读数据→AI生成→创文档→发群消息→三线发卡→建任务→标记完成

**量化结果**：全自动执行，从触发到三线推送完毕约15-30秒（含DeepSeek API调用）。

## 四、技术架构（面试可展开的点）

### 4.1 为什么用并查集（Union-Find）而不是简单排序？

**问题场景**：生产车间每天有产能上限（约5-7单/天），当某天排满后，后续订单需要顺延到下一个工作日。如果简单排序后顺序分配，当一个订单溢出时需要遍历后续所有日期找空位——最坏情况 O(n²)。

**并查集方案**（`apply_capacity_scheduling`）：

```python
overflow: Dict[date, date] = {}  # 满的日期 → 下一个可用的日期

# 路径压缩：跳过所有已满日期
for order in orders:
    d = target_day
    while d in overflow:
        d = overflow[d]     # 跳过满的日期
    if capacity[d] >= qty:
        assign(order, d)
        if is_full(d):
            overflow[d] = next_working_day(d + 1)  # union操作
```

**效果**：
- 每个日期被跳过一次后，通过路径压缩直接指向下一个可用日
- 时间复杂度从 O(n²) 降到 O(n·α(n))，其中 α(n) 是阿克曼函数的反函数，在实际数据规模下 ≈ O(n)
- 365天安全上限防止无限循环（理论上不可能出现，但防御性编程）

**面试中可以画图的点**：可以把每天想象成一个小盒子，盒子满了就贴一个箭头指向下一个盒子。当太多订单都在找同一天时，路径压缩让它们"跳过去"而不是"一格一格爬过去"。

### 4.2 为什么用difflib模糊匹配而不是调LLM？

**问题场景**：客户输入"城市花园消防"但合同里写的是"城市花园二期消防远程控制项目"，需要匹配。

**选difflib的理由**：
1. **延迟**：difflib匹配本地计算 < 1ms；调LLM（DeepSeek API）往返 2-5秒。查询场景用户体验要求秒级响应
2. **成本**：difflib零成本；LLM每次调用有token费用。日均100次查询的话LLM方案有持续开销
3. **确定性**：difflib的SequenceMatcher对同一输入始终返回相同结果，方便调试和回归验证；LLM输出有随机性
4. **够用**：订单匹配本质上是短文本相似度计算（20字以内的项目名称 vs 客户口语化输入），不需要语义理解能力

**补充方案**：当difflib匹配到多个候选（≥2条）时，用**消歧卡片**让用户选择，把模糊匹配的歧义通过人机交互消除，而不是赌哪个最像。

### 4.3 为什么需要"今日数据校验锁"？

**背景**：日报机器人每天早上自动读取日报表最新行，生成日报推送。如果前置排单系统挂了（前一天没有写入数据），机器人会读到前天甚至更早的旧数据，然后生成一份"看起来正常但数据是旧的"的日报发出去。

**校验锁机制**（`get_today_report_row`）：
```
1. 倒序取最新1行（按排单运行时间降序）
2. 提取该行的"日期"字段
3. 如果日期 ≠ 今天 → 报警
4. 供应链铁律：宁可不发报表，绝不能发错报表
```

当前实现是软报警（日志输出+继续执行），代码中已预留硬阻断开关（取消注释一行即可启用），可以根据业务容忍度切换。

**为什么不用Redis/数据库做状态存储？** 因为系统设计为单服务器部署（飞书多维表格本身就是SaaS数据层），加Redis会引入额外的运维复杂度，而日报表的"日期"字段天然就是状态标记。

### 4.4 信息隔离设计（客户看到什么 vs 内部看到什么）

两个机器人虽然共用同一套数据底座（飞书多维表格），但面向客户和面向内部的回复内容完全不同：

| 维度 | 客户订单查询机器人 | 内部供应链AI助手 |
|------|------------------|-----------------|
| 部署方式 | WebSocket长连接（lark-cli子进程） | Webhook回调（FastAPI路由） |
| 独立App | 是（独立飞书应用，独立token） | 是（独立飞书应用，独立token） |
| 可见数据 | 仅该客户名下的订单交付状态 | 全部订单、库存、产能、财务数据 |
| 回复语言 | 面向客户的口语化描述 | 内部术语（SKU、BOM、包干/单采） |
| 典型问题 | "我的订单什么时候发" | "库存缺什么""今天排了多少单" |
| 能查财务数据 | 不能 | 能 |
| 能看库存细节 | 不能 | 能 |

隔离的关键不在于代码层面做权限控制（不现实——都是一个API Token读表），而在于**两个机器人是独立的飞书应用**，分别部署在不同的飞书群，接收不同人群的消息。客户无法进入内部群，内部员工不会在客户群问敏感问题。

### 4.5 AI安全性设计（非程序员用AI写代码的安全底线）

作为一个不会写代码的人，用AI生成了全部约10,000行Python代码，安全性从第一天就是最高优先级——因为我自己看不懂每一行，出问题了我修不了。以下是贯穿整个系统的安全策略：

**1. 财务数据的"AI禁区"机制**

- **计费规则主表只读**：代码中明确硬编码"禁止AI改写"约束（`scheduler_api.py:111-112`），系统没有任何代码路径会写入计费规则表。计费规则（单价、阈值、计费方式）是财务核算的基准数据，一旦被AI误改，整个月的核算都会出错。这条规则确保AI只能读规则、按规则算，不能改规则。
- **人工核对金额锁定**：财务人员手动填写的"人工核对金额"是该合同的终极锁——一旦非空且非零，该合同在同步、核算、回写三个环节全部跳过。这是AI生成代码的最后一道防线：即使核算逻辑有bug导致某合同算错，人工修正后锁定，AI再也不会覆盖它。
- **同步时字段保护**：同步操作更新6个基础字段（合同编号、日期、客户名等），但绝不覆盖5个人工维护字段（项目类型、备注、AI项目金额、人工核对金额、AI费用检查）。同步逻辑用 `merge` + `fillna` 实现"以现有值为准"，而非直接覆写。

**2. 数据输入边界的安全校验**

- **OA→Excel→飞书的隔离链路**：OA是唯一数据源，数据从OA导出Excel后再导入飞书。这个手动环节看似低效，但实际上是安全边界——AI系统永远不直连OA数据库，即使飞书侧代码出了严重bug，也不会污染OA主数据。
- **导入时的字段清洗**（`parse_feishu_field`）：飞书API返回的字段值可能是富文本数组 `[{"text":"...","type":"text"}]`、嵌套dict、纯数字等多种格式，统一清洗后再使用。防止AI生成的代码遇到非预期格式时崩溃或产生错误结果。
- **数值安全转换**（`safe_numeric`）：所有从飞书表读取的数值字段统一过 `safe_numeric`，处理 None、空字符串、NaN、非数字字符串等边界情况，避免 `float(None)` 这类崩溃。

**3. 防止AI"胡编"日报**

- DeepSeek用于日报摘要生成（自然语言润色），但**日报的原始数据全部来自飞书表的结构化查询**，AI不参与数字计算
- "今日数据校验锁"确保日报数据源是今天的——即使AI把昨天的旧数据"写得很漂亮"，日报机器人也能识别并报警
- 日报生成失败不影响排单和核算系统运行（独立进程 `ai_daily_agent.py`）

**4. 并发与数据一致性保护**

- **文件锁互斥**（`schedule_global_lock`）：用 `os.open(O_CREAT | O_EXCL)` 确保同一时刻只有一个排单实例在运行。防止两个排单任务同时写同一张表造成数据交错
- **飞书API批量写入**：单次最多3批、每批500条，避免飞书API超时导致部分写入成功部分失败的数据不一致
- **Token预刷新**：提前5分钟刷新飞书access_token，避免在高负载时token恰好过期导致请求失败

**5. 独立审计脚本（最后的兜底）**

- `audit_rules.py` 是一个完全独立于核算流程的检查脚本，可以随时手动运行
- 6项检查覆盖：数据完整性、设备费规则、电话规则、关键词匹配、计费覆盖、汇总统计
- 设计意图：即使核算代码有bug、漏算或错算了某些合同，审计脚本能回溯发现——不依赖核算流程本身的结果，独立交叉验证

**6. 凭证管理**

- 所有API密钥、表ID、Webhook URL从 `.env` 文件读取，不硬编码在源码中
- `.env` 在 `.gitignore` 中，不提交到Git仓库
- 双机器人使用独立的飞书应用App ID和App Secret，权限最小化——客户机器人只有读订单表的权限，内部机器人才有写日报/发任务的权限

**面试中可以这样讲**：*"我知道自己不会写代码，所以整个系统的设计原则是'安全第一、功能第二'。财务数据有三道锁：计费规则表AI只读不写、人工核对金额锁定、同步时字段保护。AI生成的日报有今日数据校验锁——宁可不发也不发错的。审计脚本是独立于核算流程的，即使核算代码出了问题我也能发现。这些安全机制不是事后加的，是从第一天设计时就定下来的——因为我承担不起AI代码搞乱财务数据的后果。"*

## 五、局限与演进（诚实说）

### 当前已知的技术债务

1. **单体文件架构**：所有核心逻辑在 `scheduler_api.py` 一个文件（5000+行）。好处是"一个文件能看懂全貌"适合单人开发，坏处是代码导航和测试困难。如果团队扩大，需要按模块拆分。

2. **没有自动化测试框架**：当前验证靠 `verify_patch.py` 中的 ad-hoc assert + `audit_rules.py` 的独立审计脚本。没有单元测试/pytest/CI pipeline。原因是开发阶段需求变动快，测试维护成本高于直接跑一遍看结果。

3. **文件锁而非分布式锁**：`schedule_global_lock` 用 `os.open(O_CREAT | O_EXCL)` 实现互斥，依赖文件系统。单机部署够用，但如果未来要水平扩展需要换成Redis锁或数据库锁。

4. **关键词匹配硬编码**：AC-RB800的6组关键词→Spec_ID映射写死在代码里。如果未来增加新产品线（RB900等），需要改代码而不是改配置。

5. **飞书API频率限制无重试**：当前遇到429限流会直接失败，没有实现指数退避重试。日均50-100单量暂时遇不到限流，但量上去了需要加。

6. **内存缓存无持久化**：token缓存、字段schema缓存都在内存中，进程重启后需要重新加载。

7. **报表机器人软报警**：今日数据校验锁当前只打日志不阻断，有概率在排单系统挂掉后发出旧数据日报。

### 下一步优化方向

1. **计费规则表的关键词配置化**：把关键词→Spec_ID映射从硬编码改为读计费规则表的一个新字段（如"匹配关键词"列），新产品不需要改代码

2. **拆分为微服务**：排单引擎 / 财务核算 / 客户服务 / 日报 四个独立进程，各自独立部署和重启

3. **引入任务队列**：用Celery或简单的Redis Queue替代同步HTTP调用，财务核算等长任务异步执行，前端轮询结果

4. **加自动化测试**：至少覆盖 `_match_spec_id`（Spec_ID匹配）、`_run_finance_calculate`（核算逻辑）、`apply_capacity_scheduling`（产能调度）三个核心函数的单元测试

5. **监控告警**：接入飞书群通知，排单失败/核算异常/飞书API报错时自动推送告警

## 六、面试叙述线（STAR结构）

> 以下段落可以直接用于面试中回答"请介绍一个你用技术解决过的复杂业务问题"。语速适中约2-3分钟讲完。

---

**Situation（背景）**：

我在一家消防设备公司做供应链运营。公司的核心业务系统是OA，销售订单、库存、BOM都在OA上。日常工作每天大约10个订单，人工排单要1-2小时。但真正的痛点是两个：第一，旺季或活动期订单会突然飙升到30+单/天，人工根本排不过来；第二，月底财务核算要在OA里导出3张表，手工匹配计费规则、区分包干和单采，光核算就要2小时。OA上加一个字段要IT排期等好几周，我们等不起，所以我决定自己在飞书上搭建一套快速验证和自动化系统。

**Task（任务）**：

我的目标是：在飞书上自建一个辅助系统，把OA导出的数据快速变成排单结果和财务核算结果，同时加上客户自助查单和自动日报推送，让高峰期不再成为瓶颈。技术选择上，必须能快速迭代（不能用OA那种几周排期的节奏），操作必须简单（我自己每天用），而且要能独立完成——我不会写代码，但我会用AI。

**Action（行动）**：

我选择了FastAPI做后端（Python框架），飞书多维表格作为数据层（11张表），用Claude和DeepSeek生成了全部代码（约10,000行），花了约3个月从零搭建到上线。

这里有几个技术决策值得展开：

第一，排单算法我用了并查集（Union-Find）数据结构而不是简单排序。生产车间每天有产能上限（约5-7单），当一个日期排满了，后续订单需要跳到下一个工作日。简单排序处理溢出要O(n²)，并查集通过路径压缩做到O(n)。平时10单人工还能应付，但30+单高峰期时人工逐个排极易算错日期——并查集让系统30秒就能出结果，这是从1-2小时压缩到10分钟的关键。

第二，财务核算的Spec_ID匹配我用了三层策略：精确匹配→别名模糊匹配→关键词规则匹配。没调LLM，因为difflib本地计算1毫秒出结果，零成本，而且结果是确定性的——财务核算不能有"有时对有时不对"的不确定性。

第三，我做了信息隔离——客户查单机器人只能看到自己公司的订单，回复用的是"预计X月X日发出"这种客户语言；内部供应链机器人能看到全部数据，用的是"SKU缺货""包干超阈值"这种内部术语。两个机器人是独立的飞书应用，通过不同的群来隔离人群。

第四，AI安全性从第一天就是设计的核心。因为我知道AI生成的代码可能有bug而我修不了，所以整个系统有三道财务安全锁：计费规则表AI只读不写（避免篡改价格基准）、人工核对金额锁定（人工确认后AI永久跳过）、同步时字段保护（5个人工字段绝不覆盖）。还有一个独立的审计脚本，即使核算代码出了问题，我也能回溯发现——不依赖核算流程自己的结果。

**Result（结果）**：

系统上线后，排单从每天1-2小时→约10分钟（3分钟导入+30秒排单+人工审核），财务核算从2小时→5分钟，客户查单从5-10分钟→3秒自动回复，日报从20-30分钟→全自动。订单高峰期不再是人仰马翻的时刻——系统30秒就能出结果，剩下的时间用来人工审核和沟通确认。

但最有价值的不是省了多少时间。而是：1）OA一侧的字段修改要等IT排期几周，飞书这边我自己几分钟就能调，迭代速度快了一个数量级；2）财务的"人工核对金额锁定"让AI和人工各司其职——AI出初稿，人工确认后锁定，AI永远不覆盖人工确认过的数字，财务团队从"不敢相信数字"变成了"审核确认即可"。
