## 6 个 P0 致命问题

| # | 问题 | 来源 | 修订方案 |
|---|------|------|---------|
| 1 | **内存 dict 重启即丢失** — report 已写入日报表，不应再造缓存 | 架构师+技术 | 直接从 `TABLE_ID_DAILY_REPORT` 读取 report |
| 2 | **按钮 URL 不能 POST** — 飞书卡片按钮只能 GET 跳转 | 架构师+技术 | 改为**飞书卡片回调按钮**（应用后台配置 + POST 回调 FastAPI） |
| 3 | **缺超时自动降级** — 排单员请假 = 群通知永远不发 | 运营总监 | **移到 Must-have**：30分钟未确认 → 自动群发 + 标注"系统自动推送" |
| 4 | **紧缺物料 Top 5 太少** — 12个SKU只展示5个，排单员要点进总表 | 运营总监 | 改为展示全部缺货SKU（或至少Top 10 + 滚动），增加绝对缺口数量 |
| 5 | **确认行为不可追溯** — 不回写排单总表，追责困难 | 运营总监 | 日报表新增"确认推送"/"确认时间"/"确认人"字段 |
| 6 | **缺"缺口数量"** — 方案只写了"受影响合同数"，采购需要"要买多少个" | 运营总监 | 两种口径都展示 |

## 修订后的推荐技术方案

### 核心技术选型

| 决策点 | 原始方案 | 修订后 |
|--------|---------|--------|
| 按钮触发 | HTTP POST | **飞书卡片回调按钮** |
| 缓存 | dict | **飞书日报表读取**（report 已写入） |
| 降级 | 不做 | **30分钟自动群发 + 标注** |
| 紧缺物料 | Top 5 | **全部缺货SKU + 缺口数量** |

### 实现步骤（~80行，单文件 scheduler_api.py）

1. **飞书应用后台** → 配置"消息卡片请求网址" → `POST /feishu/card_callback`
2. **按钮改造**：`url` → `value`，飞书发送回调到 `/feishu/card_callback`
3. **新增回调端点**：验证飞书签名 → 解析 batch_id → 读日报表 → 发给 Track1+Track3
4. **日报表**：增加"已确认推送"字段，防重
5. **超时降级**：30分钟未确认自动触发
6. **紧缺物料改造**：展示全部缺货SKU及缺口数量

### Non-goals（明确不做）
- ❌ 不自建 HTTP 确认端点
- ❌ 不使用 dict/Redis 做缓存
- ❌ 不跳过超时降级机制
