# 排单引擎 + 财务模块优化方案 — 实施汇总

> 日期：2026-06-19 | 状态：方案阶段，待讨论确认后执行

---

## 一、背景：我们发现了什么问题

排单引擎设计初衷是"持续增量排单"，但实际使用中变成"攒大单→批量缺口扫描→通知生产"。演进中暴露了核心问题：

| # | 问题 | 表现 |
|---|------|------|
| 1 | **缺货到货日期不可信** | 生产部门只有一人+实习生，承诺的到货时间不准，却硬要系统输出"预计发货日期" |
| 2 | **对账表数据不全且有残留** | 每次只导入当期订单，历史已完成合同不在表里；Upsert 同步后旧明细行残留，汇总金额可能出错 |

参考 ERP 体系的标准做法（MRP 计划→执行记录→差异对账三层分离 + 财务累积锁定机制），结合自身现实约束，提出以下优化方案。

## 三、排单模块改动

### 改动 1：排单结果按"可发状态"分类

**目标**：不再给缺货合同硬塞猜出来的日期，诚实标注状态。

**飞书侧**：AI 排单总表加一个字段

| 字段 | 类型 | 选项 | 来源 |
|------|------|------|------|
| 发货状态 | 单选 | 全部可发 / 部分可发 / 等待中 | 系统自动 |

判断逻辑：
- 缺货SKU数 = 0 → **全部可发**，AI建议发货时间正常排产能
- 缺货SKU数 > 0 且 < 总SKU数 → **部分可发**，AI建议发货时间 = 有货部分的排期
- 缺货SKU数 = 总SKU数 → **等待中**，AI建议发货时间留空

**代码侧**：

```
文件：scheduler_api.py
位置：summary 构建循环（约 3877 行）

在 summary_rows 构建时加：
"发货状态": (
    "全部可发" if shortage_sku_count == 0 else
    "部分可发" if shortage_sku_count < (sku_count or 1) else
    "等待中"
),

对于"等待中"状态，AI建议发货时间 = ""
```

**效果**：打开排单结果，一眼看到谁能发谁在等。不用手动推不靠谱的日期。

### 改动 2：缺货清单导出 Excel

**目标**：生产部门不看飞书，生成按产线排版 Excel，打印即工单。

**为什么不做飞书推送**：生产车间工作介质是纸质单据，强推数字化就是做没人用的功能。

**功能**：排单管理页面新增「导出缺货工单」按钮。

**Excel 样式设计**：

├────┬──────────┬────────────────┬──────┬──────┬──────┬───────┤

├────┴──────────┴────────────────┴──────┴──────┴──────┴───────┤

**分区规则**：
- 有合同编号的 → 「订单缺货」区，显示合同编号+项目名+缺货数量

## 四、财务模块改动

### 改动 3：对账同步改为「首次同步 + 手动重置」 ⚠️ 涉及 ADR

**背景**：当前 `/finance/sync` 是 Upsert。同一合同二次导入时有两种完全不同的意图——部分发货后的正常重导（不应更新财务表）vs OA 数据修正后的重导（应该更新财务表）。靠"合同是否存在"这一个条件分不出来。

**决策**：同步默认跳过已有合同，但提供手动重置机制——人在飞书表上改一个状态，触发重同步。

**飞书侧**：财务对账总表加一个字段

| 字段 | 类型 | 选项 | 说明 |
|------|------|------|------|
| 同步状态 | 单选 | 已同步 / 待重新同步 | 同步后自动标「已同步」；需重同步时人工改为「待重新同步」 |

**同步流程（改后）**：

```
1. 读销售订单明细表 → 获取本次合同列表
2. 读对账总表 → 分出「已锁定」「已同步」「待重新同步」
3. 已锁定合同 → 跳过
4. 已同步合同 → 跳过（日常重复导入不影响财务表）
5. 待重新同步 → 覆盖更新（人工标记，用于 OA 数据修正场景）
6. 不在财务表 → 首次同步，写入，标「已同步」
```

**业务场景覆盖**：

| 场景 | 操作 | 财务表行为 |
|------|------|-----------|
| 首次导入 7 行 | 同步 | ✅ 写入 7 行，标「已同步」 |
| 发了 4 个剩 3 个，二次导入 | 已同步→跳过 | ✅ 7 行不动 |
| OA 漏了 2 个 SKU 改完重导 | 人工标「待重新同步」→覆盖更新 | ✅ 按最新 OA 数据重写 |
| 人数核对完 | 填写人工核对金额→锁定 | ✅ 永久冻结 |

**代码侧**（`/finance/sync`）：

```python
for cid in all_import_contracts:
    fin_row = get_finance_summary_row(cid)
    
    if fin_row and fin_row["人工核对金额"]:
        continue  # 已锁定，跳过
    
    if fin_row and fin_row.get("同步状态") == "已同步":
        continue  # 正常跳过，不动
    
    if fin_row and fin_row.get("同步状态") == "待重新同步":
        # 覆盖更新，重置为已同步
        upsert_to_finance(cid, rows)
        update_sync_status(cid, "已同步")
        continue
    
    if not fin_row:
        # 首次同步
        upsert_to_finance(cid, rows, sync_status="已同步")
```

**效果**：
- 部分发货场景：财务表不动
- OA 修正场景：人手动改「待重新同步」→ 点同步 → 按最新数据覆盖
- 不需要代码猜意图——人控制重同步时机
- 和「人工核对金额→锁定」同一个设计哲学：人工在关键节点做决策

### 改动 4：老板经营看板

**目标**：同一套数据底座，复用为老板的经营视图——不只是财务，交付和订单一并上。

**飞书侧**：财务对账总表加一个预留字段

| 字段 | 类型 | 说明 |
|------|------|------|
| 成本金额 | 数字 | 🔒 预留，暂不填 |

**看板布局**：

```
┌──────────────┬──────────────┬──────────────┐
│   📦 交付     │   💰 财务    │   📋 订单    │
├──────────────┼──────────────┼──────────────┤
│ 本月可发订单  │ 本月收入     │ 本月新签合同  │
│ 本月缺货SKU  │ 待确认收入   │ 在途订单金额  │
│ 已发货件数   │ 客户收入排行  │ 紧急订单数   │
│ 物流签收率   │ 月度收入趋势  │ 订单来源分布  │
├──────────────┴──────────────┴──────────────┤
│  🔴 关注：HT008 缺货超7天 │ 库存预警3项    │
└─────────────────────────────────────────────┘
```

**数据来源（全读现有表，零新增表）**：

| 卡片 | 读哪张表 | 计算 |
|------|---------|------|
| 本月可发订单 | AI 排单总表 | COUNT(发货状态="全部可发") |
| 本月缺货 SKU | AI 排单总表 | 缺货SKU列表汇总 |
| 已发货件数 | AI 发货总表 | COUNT(是否发货="是") |
| 物流签收率 | AI 发货总表 | 签收数/总发数×100 |
| 本月收入 | 财务对账总表 | SUM(锁定合同 AI项目金额) |
| 待确认收入 | 财务对账总表 | SUM(未锁定 AI项目金额) |
| 客户收入排行 | 财务对账总表 | 按客户 SUM |
| 月度收入趋势 | 财务对账总表 | 按月 SUM |
| 本月新签 | 销售订单主表 | COUNT(本月下单) |
| 在途订单金额 | 财务对账总表 | SUM(未锁定 AI项目金额) |
| 紧急订单 | 销售订单主表 | COUNT(是否紧急="是") |
| 库存预警 | 库存快照表 | 库存<安全库存的 SKU |

**展示方式**：
- 飞书多维表格内置「仪表盘」模块，拖拽建图表，无需写前端
- 或在内部供应链助手加指令，老板 @机器人 说"经营看板"返回汇总卡片

**成本端扩展（后续）**：成本金额字段接入采购数据后，可出毛利/毛利率。

**面试金句**：
> "老板看板不是我重新做了一个系统，而是把排单、发货、财务三张核心表的数据做了横向汇总。同一个数据底座，服务了排单调度、财务核算、老板决策三个完全不同的场景——产品复用性最好的证明。"

### 8.3 面试叙述：ROI 怎么讲

不要只报数字，分层讲：

**一层·时间**：
> "三个核心模块月均节省约 50 小时，投入不到 400 块，首年 ROI 过万。但说实话，在年流水过亿的公司里，省 50 个小时不是这个项目最大的价值。"

**二层·风险**：
> "排单高峰期漏排一个合同，或者财务核算错一笔包干/单采分类，代价比省时间大得多。系统消除了两个系统性风险：人工排单约 5% 漏检率→系统零漏检；财务三道安全锁确保 AI 不覆写人工确认的数字。"

**三层·响应速度**：
> "OA 改一个字段要 IT 排期几周，飞书侧我几分钟就调。这个迭代速度差是整个系统最值钱的能力——它不是一次性的提效工具，而是一个可以持续进化的业务操作系统。"

### 8.4 两个不用的模块怎么讲

> "日报和内部助手建了但我自己用得少——日报的推送频率和我看表的节奏不匹配，助手的使用场景太窄，大部分查询我动手指比打字快。这两个不算失败，它们验证了'自然语言交互'在这个场景下不是最优解，帮我收敛了后续投入方向。"

## 九、面试叙述线（整合版）

**排单引擎进化**：

> "排单引擎上线后，我发现一个核心矛盾：缺货 SKU 的到货时间不可信——生产部门只有一个正式工带实习生，承诺的日期经常不准。但系统却硬要给每个合同算出一个'预计发货时间'。
>
> 我的选择不是去优化预测模型，而是诚实面对不确定性。把排单结果拆成三类：有货的给精确排期，缺货的不假装预测标'等待中'，同时把缺货清单导成 Excel 给生产当工单——不对生产部门强推飞书，因为他们的工作介质就是纸。
>
> 后来我系统性地审计了代码，修复了 5 个严重问题（库存导入原子性、API 限流重试、Spec_ID 规范化、财务核算回写校验、依赖补全），确保核心数据路径不会静默出错。"

**财务模块进化**：

> "财务月结全流程 3-5 天，包含和总代理对账、特殊情况审核等需要人判断的环节。系统只接手机械劳动——480 行数据逐条匹配计费规则、分包干单采、逐行乘法汇总，手工 3-4 小时压缩到 5 分钟，让我从算数变成决策。
>
> 同步逻辑用了'首次同步 + 手动重置'机制——日常导入不影响财务表，OA 数据修正时人工标'待重新同步'触发覆盖。配合人工核对锁定，财务数据有三道保障。
>
> 后来我把排单、发货、财务三张核心表横向汇总成老板经营看板——交付、财务、订单三个模块一个页面，全读现有表零新增。"
